# Synchronize tracking systems

Use this procedure for `sync` and for tracker updates requested by `start`, `pr`, or `close`. Scope reads and writes to the selected tasks, verified GitHub repository, and verified Trello board. Preview proposed changes if authorization is missing. Apply only the operations already authorized for those targets and that data.

## Identity and field ownership

- Use the project's established task key and mapping if they are unambiguous. For new tasks in a project without a convention, assign one stable ID during planning, unique within the project, and put a standalone `Workflow ID: <id>` line in each new record at creation. The task template includes this field. Keep the canonical card and issue URLs on both records where authorized. Preserve existing descriptions and user edits.
- Identify records first by a verified cross-link, then by an exact stable ID within the selected board or repository. A title is a hint for a manual match. Check all relevant pages and include closed issues and archived cards. If links disagree, multiple records have the ID, or an existing match is plausible but unconfirmed, stop changes for that task and show the alternatives. An incomplete search never establishes absence.
- Follow the team's field ownership rules. A workable default is the task's original tracker for requirements and acceptance criteria, Trello for stages and assignments where it is the agreed board, and GitHub for branches, PRs, checks, and merge evidence. Use GitHub Issues for task state when Trello is deliberately unused. Only mirror fields agreed for both sides, and never interpret a closed issue as proof that a task is Done. Map assignees by a verified identity mapping. If a trusted field has competing edits and the owner cannot be determined, ask which value should win.

## Apply and resume

1. Resolve existing records for each selected task and produce the operations needed to reach the approved state. Record the intended repository or board, task ID, records, access limitations, and links or fields to change. Keep private data on the permitted side when linking tools with different visibility. Copy only the data authorized for the destination.
2. If both records are absent and in scope, create them one at a time, starting with the task's source tracker or the first destination the user approved. Include the stable ID in each create request. Recheck absence immediately before each create. Save each confirmed record ID and URL before proceeding. Resolve both records before adding reciprocal links. Update only missing links or fields that differ. Refresh records before edits and preserve concurrent human changes. Coordinate a single writer per task when multiple sessions could create records for it.
3. After a timeout or partial failure, look up the attempted operation by stable ID and known record URLs and use the existing result if found. Never retry a create with an ambiguous outcome while you cannot confirm whether the original request took effect. If one side succeeded, preserve it and reconcile the other side on the next authorized run. If one tracker is deliberately unused, complete only the relevant side. If a required tracker is unavailable, report its pending actions without redirecting the writes to a different board or repository.
4. Verify assigned IDs, target lists, and links against provider responses or fresh reads. Report created, updated, already matched, and pending operations with exact links. A second run on the same state should produce no writes. Use [close](delivery.md#close) for transitions that would put a task in Done, including closing issues or placing cards directly in the Done list.

## Provider capabilities

Prefer the connected tool for the relevant operation. With an authenticated `gh` fallback, pass the verified `[HOST/]OWNER/REPO` explicitly as `--repo`; use `gh issue view` and complete listing or paginated API reads to verify matches across states. Use `gh issue create` or `gh issue edit` for authorized changes and supply multiline bodies via a file. For Trello, use the configured connection to read the board's lists, cards, and member IDs. Create with `POST /1/cards` using the verified `idList` and update via `PUT /1/cards/{id}`. Reuse existing checklists or attachments and create them only when needed and authorized. If a trusted browser is the only connection and has the required permission, the same target, identity, and verification checks apply. Keep credentials in the configured environment or connector.
