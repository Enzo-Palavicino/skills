# Deliver and close a task

## start

1. Resolve the exact task from its ID, card, or issue and read the accepted criteria, owner, and dependencies. Apply the project's Definition of Ready, or check at least that the scope and criteria are clear and blocking dependencies are resolved. Verify dependency completion from the agreed evidence. If blocked, report why before changing the branch or trackers.
2. Verify the integration branch and refresh its Git reference from the correct remote. Check the working tree, existing branches, and `git worktree list`. Reuse a branch already associated with this task if its identity is certain. If creating one, use the project's naming rule, or a name such as `feat/TW-014-password-reset` from the verified integration ref. For a local-only project, use the agreed local ref. Never reset an existing branch. Use an isolated worktree when the current checkout contains unrelated work or a parallel task needs its own checkout. Preserve all uncommitted changes and report where the task branch is checked out.
3. Outline the implementation, relevant tests, and any edits likely to overlap with another task. Implement or commit only when requested. Respect the project's Conventional Commit scopes and types. In the absence of a scheme, use a concise subject such as `feat(auth): add password reset` or `fix(auth): reject expired reset links`. Build commits from relevant changes only and omit AI coauthor trailers.
4. After verifying the branch, record its name or verified remote URL and apply stage updates in the agreed tracker records as authorized using [synchronization](sync.md). For Trello, move the card to the verified In progress list. If a required update lacks permission, keep the local branch, report the pending update, and keep any other writes within their own approved targets. Report the branch, worktree, verified base, and any tracker links or updated stages.

## pr

1. Resolve the task, verified integration branch, source repository, and head branch. Read the intended diff and commits. Check the acceptance criteria, applicable tests and build, and any needed migrations or documentation. Report the checks that ran, those that failed, and those that could not run. Distinguish local results from GitHub checks. Surface gaps or blockers before proposing a ready PR. Use an explicitly authorized draft if the user wants feedback with known gaps.
2. Find active PRs for the exact source repository, head branch, destination repository, and base. Reuse a matching PR and report its URL. If a PR exists for the task with a different base or head, confirm the intended target before creating another or changing it. Use the project's PR template or [the supplied template](../assets/pull-request.md). Link the work items, describe the change and evidence, and identify any reviewers required by the project. Use ordinary links to tracking issues when separate closeout is required, so merging the PR does not bypass it.
3. If requested to prepare only, show the title, body, base, head, and test evidence. To publish, proceed only with the authorized push and PR creation or update, preserving the known remote head and existing PR content. Never force-push. Prefer the GitHub integration and fall back to `gh pr create --repo OWNER/REPO --base BASE --head HEAD --title TITLE --body-file BODY_FILE` with verified values and the host when applicable. Use `OWNER:BRANCH` for a supported fork head, and verify that the branch exists on the intended remote first. If the create response is ambiguous, look up the exact PR before any retry.
4. Confirm the PR's URL, head, base, and draft status. Report current CI without waiting indefinitely or presenting pending checks as passed. Link the PR and, where authorized, advance the tracker to In review and request eligible reviewers. If available, `review-pr` can help with an evidence-based review when the user requests it. An agent's verdict does not stand in for required independent approval. Report any steps left pending.

## close

1. Resolve the task and all PRs needed for its acceptance criteria. Confirm each required PR was merged into the correct integration branch and record the merge or integration SHA and PR URL. Use GitHub merge metadata and the integration branch as evidence, including for squash or rebase merges. Use an alternate integration record only if the team's workflow explicitly permits it. A ready, approved, green, or merely closed PR does not establish integration.
2. Confirm the criteria, required checks and independent approvals, and the project's Definition of Done. Tie test and approval evidence to the revision the project's policy requires. Check follow-up work, documentation, migrations, or deployment evidence when the team's policy requires them. If evidence is missing or a condition failed, report the open items and leave the trackers unchanged. Example verification includes `gh pr view PR --repo OWNER/REPO --json state,mergedAt,mergeCommit,baseRefName,headRefOid,reviewDecision,statusCheckRollup,url` plus required review and check details where relevant.
3. If eligible and authorized, record the integration evidence and move the card to the verified Done list and close the issue as applicable. Skip records that are already in the correct state, adding missing evidence only when authorized. Apply the recovery rules in [synchronization](sync.md) if one tracker is unavailable or one of the writes fails. Report the integration SHA, the resulting card and issue states, and any pending updates. Leave branch and worktree cleanup to a separate request.
